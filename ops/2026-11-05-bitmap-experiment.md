# PDF 位图解码实测（2026-11-05）

结论：未自然复现线上 `createImageBitmap()` 的 `InvalidStateError`。不能据此认定已修复，也不能证明线上是内存不足或 JPEG 损坏。

## 实测结果

| 场景 | 结果 | 累积保留的压缩图片字节 | 耗时 |
|---|---|---:|---:|
| WebKit 26.5，保留缓存 | 677/677 页，无异常 | 481,862,769（约 482 MB） | 105 秒 |
| WebKit 26.5，不累积缓存 | 677/677 页，无异常 | 0 | 114 秒 |
| Chromium 151，保留缓存 | 677/677 页，无异常 | 325,859,151（约 326 MB） | 56 秒 |

正常 JPEG 在 WebKit 的 `createImageBitmap` 和 HTMLImageElement.decode 两条路径均成功。人为生成的非空无效 JPEG 在前者抛 `InvalidStateError`，后者抛 `EncodingError`。因此备用解码不能修复所有坏数据。截掉后半段的样本两条路径均容错成功，不能认为任何 JPEG 截断都会失败。

已有导出资源测试：`node --test tests/export-memory.test.mjs`，7 项通过，0 失败。

## 测试范围及限制

- 本机 macOS 26.6.2，16 GiB 物理内存；390×844 视口不是实际 iPhone，也没有模拟 iOS 的内存上限。
- 复用本项目真实 JPEG 编码、位图解码、反色 Worker 和 pdf.js 渲染；只将 Sentry/Pulse 上报出口替换为空操作。没有强制制造 API 异常。
- 使用人工生成的 677 页 PDF，页面为相同噪声底图加不同页码；不是原出错文件。不同浏览器的编码输出不同，因此输入二进制文件也不同。
- 测试覆盖页面渲染到反色 JPEG 的链路，不覆盖 React UI、图片区域扫描、最终 PDF 组装与下载。
- 表中数值是压缩 Blob 的累计大小，不是进程实际内存；不保留缓存组也不代表内存立即被系统回收。
- 未改产品代码、未部署、未向生产注入测试错误、未标记线上问题已解决。

## 下一步依据

当前结果不支持直接断言“累计到 15 MB 或 111 MB 就失败”。仍需用原始文件和真实 iPhone 验证设备资源或内容差异。如果继续改诊断，应在解码失败时检查 Blob 是否可读取、JPEG 特征和备用解码是否成功，并保留真实错误，避免直接把异常归因于内存。
